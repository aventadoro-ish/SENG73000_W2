New Approach to the Scheduling Algorithm

I concluded that a custom priority queue would not be suitable for this scheduling algorithm. Its entries would need to be rearranged whenever a request was added or completed, and the target floor could change while the car was moving. Instead, I decided to use flag tables to represent the pending requests.

The tables track:

  • Upward floor requests.
  • Downward floor requests.
  • Car requests.

The scheduler also requires the following state variables:

  • The travel direction, which may be upward, downward, or stationary.
  • The dynamic travel limit, which indicates how far the elevator will travel before changing direction.
  • The current target floor, which allows external modules to detect when a new request changes the target.
  • The current floor, which is updated both externally and within the scheduling logic.

I added an initial implementation of the algorithm. Its broad behaviour is as follows:

  • If no requests are pending, the car remains stationary.
  • If one request is pending, the car travels to that request.
  • If the car is already moving when a new request arrives:
    • A request in the current direction of travel and closer than the dynamic travel limit may become the new target floor, unless the existing target is closer.
    • An opposite-direction request beyond the current dynamic travel limit extends the limit and may become the new target, unless the existing target is closer.

The scheduler runs whenever a new request is added or the elevator stops at a floor to service requests.

I also added a function that clears requests when the elevator stops at a floor. The current implementation assumes that, when an upward-moving car stops, passengers who requested that floor exit and passengers who want to travel upward enter.

Manual Test Interface

I asked ChatGPT to generate the initial console-based test-interface code from my specification[1]. I did not use generative AI for the subsequent debugging and troubleshooting. My prompt was:

I am developing a scheduling algorithm for an elevator with request-direction prioritization: a user on a given floor can request the car to travel either upward or downward. I want to test the algorithm manually by providing console commands to the module. Can you implement a manual test function for me?

The requested interface included:

  • The tick command advances the simulation by one step.
    • If the car is moving, the command increases or decreases the current floor number and calls update_car_position().
    • If the car reaches the floor returned by get_target_floor(), the command stops the car and calls register_car_stop().
  • The FdD command adds a floor request.
    • F identifies the request as a floor request.
    • d is the requesting floor number, from 1 to NUM_FLOORS.
    • D is either U for upward travel or D for downward travel.
  • The Cd command adds a car request.
    • C identifies the request as a car request.
    • d is the requested floor number, from 1 to NUM_FLOORS.
  • The print command displays the Scheduler object's internal state and the external simulation variables in a readable format.
  • The exit command stops the simulation.

During troubleshooting, I added another rule: a car request in the current direction of travel extends the dynamic travel limit when its floor lies beyond that limit. This change resolved a minor issue and provides reasonable elevator behaviour.

Six-Floor Test Case

I tested the scheduler with three-floor and six-floor configurations. The six-floor test used the following sequence:

  1. A downward floor request is made from floor 3.
  2. While the elevator is moving, a downward floor request from floor 6 and an upward floor request from floor 4 are added.
  3. The elevator first travels to floor 4 to pick up the upward-travelling passenger.
  4. The new passenger requests floor 5 through the car interface.
  5. The elevator travels to floor 5 and drops off the passenger.
  6. The elevator travels to floor 6 and picks up the downward-travelling passenger. It reaches the dynamic travel limit and reverses direction.
  7. The new passenger requests floor 2 through the car interface.
  8. The elevator travels to floor 3 and picks up the downward-travelling passenger, who requests floor 1.
  9. The elevator travels to floor 2 and drops off the passenger from floor 6.
  10. The elevator travels to floor 1 and drops off the passenger from floor 3.

The test passed successfully. Two demonstration videos still need to be added.

A simple FIFO implementation with basic prioritization would require 16 time steps: six for the initial floor-3 request, five for the intermediate upward request, and five for the downward request from floor 6. This estimate assumes that the intermediate request is serviced before floor 6, which itself requires some prioritization. My algorithm completed the same scenario in 11 time steps.
