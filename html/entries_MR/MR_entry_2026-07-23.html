Raspberry Pi Workflow When Switching Units

When I used a different physical Raspberry Pi, SSH displayed the following warning:

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

The warning appears because the new Raspberry Pi presents a different SSH host key for the same hostname. I removed the saved key by running:

ssh-keygen -R lif.local

I then recreated the SSH keys by following the process documented in RPi Deployment Setup for VSCode Build Task.

Database Integration

I defined the interface for a DB class for Nick to implement. The outline and function descriptions were:

class DB {
    // Database state and implementation-specific variables

public:
    enum class Tables {
        CAN_LOGS
        // Additional tables
    };

    enum class OperationMode {
        NORMAL,
        SABBATH,
        MAINTENANCE,
        FAULT
    };

    std::string map_table_name(DB::Tables table);

    /**
     * @brief Add a database entry containing a CAN frame.
     * @param id Message identifier defined by the CAN protocol.
     * @param data Pointer to an integer array of the given length.
     * @param length Length of the data array.
     * @return 0 if successful, or -1 if an error occurs.
     */
    int log_can_message(int id, int* data, uint8_t length);

    /**
     * @brief Read a newly requested floor from the database.
     * @return 0 if no new request exists, -1 if an error occurs,
     * or the requested floor number otherwise.
     */
    int read_floor_request();

    /**
     * @brief Read the current operating mode from the database.
     * @return The current operating-mode value.
     */
    DB::OperationMode get_operation_mode();

    /**
     * @brief Check whether the database is active and reachable.
     * @return true if connected, or false if disconnected.
     */
    bool is_db_connected();
};

I implemented table-name lookup with a function that maps enumeration values to strings:

std::string DB::map_table_name(DB::Tables table) {
    switch (table)
    {
    case Tables::CAN_LOGS:
        return std::string("can_table_name");
    default:
        std::cerr << "Invalid DB table value" << std::endl;
        break;
    }
    return std::string();
}

CAN Module

The existing CAN module, pcanFunctions, provides basic communication but leaves CAN-data interpretation to the main control logic. This arrangement is difficult to extend because every instance of frame interpretation must be changed whenever the CAN protocol or supported functionality changes.

I therefore began refactoring the code into a dedicated can module. The module will:

  • Interact with libpcan.
  • Handle errors associated with the CAN hardware.
  • Interpret incoming CAN messages.
  • Provide an easy-to-use API for other modules.
    • For example, ec_request_floor accepts a floor number and the Elevator Controller's enabled status.
    • Incoming messages can be returned as structures with decoded fields. An Elevator Controller heartbeat structure, for example, contains the current position, enabled state, and moving state.

This design removes bit-level operations from the main FSM and will make it easier to add functionality during Phase 3.
