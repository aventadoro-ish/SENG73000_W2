Communication Issue with the Diagnostics Page

I prepared the following email to document a communication issue that could affect delivery of the CAN diagnostics functionality for the Phase 2 demonstration.

Draft Email

Hello Professor,

I am writing to inform you about an issue with the implementation of the CAN diagnostics page. As you know, Nick and I previously raised concerns about Rita's project contributions and the lack of clear communication concerning the tasks for which she was responsible. In short, we may not deliver the CAN diagnostics features for the Phase 2 demonstration because Rita did not clearly communicate to the rest of the group that she intended to drop the task. A full explanation follows.

After your July 15 announcement outlining the Phase 2 deliverables, I created a TODO list containing the 19 tasks that the group needed to complete. I asked the group members to assign themselves the tasks for which they wanted to be responsible. I also assigned several tasks based on my understanding of each member's current work. I assigned the I²S audio-announcement task to Rita because we had discussed it in person before the announcement, probably on July 13 or during the preceding weekend.

Nick and I continued updating the spreadsheet and taking on new tasks as we completed our existing work. Rita did not assign herself any additional tasks or update the TODO list.

During our July 20 debrief, Rita presented her I²S work and learned that all of the other tasks had already been assigned. Nick and I therefore transferred the CAN diagnostics-page task from Nick to Rita. Nick had only just started it and was occupied with other features, so this change gave Rita another project task. We discussed the expected functionality of the diagnostics page.

Rita's I²S work consisted of three Raspberry Pi configuration lines and approximately 20 lines of C++ code. Raspberry Pi I²S examples and tutorials are widely available, and a feature of this scope would normally take substantially less than a week to implement. It was the only feature on which she worked during that period.

By Wednesday, July 22, Rita had pushed the first version of the CAN diagnostics page to the GitHub repository. The page did not use CAN logging or display CAN messages; instead, it retrieved data from the unrelated Elevator Requests page. Nick provided detailed written feedback describing the changes that were required.

On Friday, Rita asked me whether she could drop the CAN diagnostics task in favour of completing a Data Communications and Networks lab, for which we are in the same group. Although the lab was a significantly smaller task, I told her that I did not object, provided that she first discussed the change with Nick because he had been leading the website and database work.

Around midnight, she sent Nick her unpushed changes through a private Discord message. Discord formatting distorted the code, and her message did not mention dropping the task; it only requested feedback. Nick asked her to resend the work as a file or correct the formatting. The following morning, a GitHub commit added only the CAN-message-log database table, with no additional work on the webpage.

As of 2:00 a.m. on July 27, Rita still had not told Nick that she was dropping the task. Nick therefore formally took over the work and began preparing the functionality for that day's demonstration.

I would like to ask you to consider this information when grading our upcoming Phase 2 submission.

There are other issues that I have not included because this email is already lengthy. If helpful, we can discuss them after today's demonstration.

Thank you for your understanding,

Matvey

FSM and CAN-Protocol Updates

Implementing the new FSM required several minor changes to the CAN protocol:

  • Elevator Controller heartbeat messages now include an is_moving bit.
    • A position value of zero is no longer used to indicate that the elevator car is moving.
  • Message ID 0x201 is reserved for a virtual door-open command, although the command is not yet implemented.
    • This message will support web-based door-open and door-close commands.
    • Web commands must have lower priority than Car Controller messages but higher priority than Floor Controller messages.
  • Message ID 0x090 indicates a fault condition to every node.

The updated Floor Controller identifiers are:

  • Floor 1: 0x301.
  • Floor 2: 0x302.
  • Floor 3: 0x303.

System Integration

Nick and I met in the lab before the demonstration to merge the project changes and resolve the remaining integration problems. We encountered and fixed the following issues:

  • The database schema on the Raspberry Pi was out of date because the latest schema had not been exported to an SQL file and installed on the Pi.
  • The Supervisory Controller received message ID 0x001 because the PCAN adapter emitted a non-frame status message that the software interpreted as a CAN frame. The can module now ignores this message type.
  • The system reported unknown CAN identifiers because the Floor Controllers had not yet been reflashed with the current firmware.
  • Scheduler integration required an Elevator Controller update so that the current floor would be reported correctly.
  • Database request completion did not work correctly because the implementation assumed that only one request could be active. Completing a request therefore overwrote the active-request state.
  • The database module issued commands that had accumulated before the FSM started. I added logic so that the FSM only executes database commands created after the program begins running.

I also implemented remote door-open and door-close control. I wired the I²S amplifier on the elevator platform and integrated Rita's announcement code so that the system announces the floor at which the elevator arrives.
