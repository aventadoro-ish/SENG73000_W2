Websockets and NodJS

The goal was to synchronize the virtual elevator on the website with the physical elevator without repeatedly polling from the browser. A Node.js program now watches the can_message_log table and pushes each new CAN entry to connected webpages through a WebSocket.

The virtual elevator does not move immediately when a website request is submitted. It waits until the Elevator Controller (EC) reports its physical position. This prevents the website from displaying movement that never actually occurred. 

website request
    -> PHP inserts a pending elevator request
    -> SC reads the request and commands the EC over CAN
    -> EC moves and broadcasts its position using CAN ID 0x101
    -> SC records the received message in can_message_log
    -> Node detects the new row
    -> Node broadcasts JSON through the WebSocket
    -> elevator_control.js moves the virtual elevator

Initial Node.js setup

I created a separate websocket folder inside the LiF Supervisor Controller web project and initialized a Node.js project. 

cd C:\xampp\htdocs\SENG73000_W2\RPi\LiF_SC

The packages have separate roles:

  • ws creates the WebSocket server in Node
  • mysql2 allows Node to query MariaDB using its Promise API
  • dotenv loads configuration values from a local .env file

The .env file stores configuration separately from server.js. The real password should not be written in the logbook or committed to GitHub.

Stage 1: basic WebSocket connection

The first stage proved that Node and a browser could open a persistent connection. The browser uses its built-in WebSocket class, while Node uses the ws package.

The basic server was created in server.js:

require("dotenv").config();

const WebSocket = require("ws");

// open the websocket server using the configured port
const server = new WebSocket.Server({
    port: Number(process.env.WS_PORT) || 8080
});

console.log("websocket server running on port " + (Number(process.env.WS_PORT) || 8080));

// run whenever a webpage connects to the server
server.on("connection", function(socket) {
    console.log("webpage connected");

    socket.send("Connected to the LiF WebSocket server");

    socket.on("message", function(message) {
        console.log("message received from webpage: " + message.toString());
    });

    socket.on("close", function() {
        console.log("webpage disconnected");
    });
});

Stage 2: watching can_message_log

After proving the socket itself, I connected server.js to MariaDB with a MySQL2 connection pool. 

const mysql = require("mysql2/promise");

// create a reusable pool for mariaDB queries
const pool = mysql.createPool({
    host: process.env.DB_HOST,
    port: Number(process.env.DB_PORT) || 3306,
    user: process.env.DB_USER,
    password: process.env.DB_PASSWORD,
    database: process.env.DB_NAME,
    waitForConnections: true,
    connectionLimit: 5,
    queueLimit: 0
});

let lastLogId = 0;
let pollTimer = null;

When Node starts, it finds the newest existing CAN row. This prevents it from broadcasting the entire table as though every old entry were new. 

async function startCanWatcher() {
    const query = `
        SELECT log_id, can_id, direction, raw_byte, source_controller, logged_at
        FROM can_message_log
        ORDER BY log_id DESC
        LIMIT 1
    `;

    const [rows] = await pool.execute(query);
    console.log("Connected to Lif_Elevator database");

    if(rows.length > 0) {
        console.log("Newest CAN entry:");
        console.table(rows);
        lastLogId = Number(rows[0].log_id);
    }

    console.log("watching for entries after log #" + lastLogId);
    pollTimer = setInterval(checkForNewCanMessages, 500);
}

Each check uses lastLogId as a prepared-statement value. Only rows with a larger ID are returned, and ascending order ensures multiple new entries are handled in the order they were inserted. 

async function checkForNewCanMessages() {
    try {
        const query = `
            SELECT log_id, can_id, direction, raw_byte, source_controller, logged_at
            FROM can_message_log
            WHERE log_id > ?
            ORDER BY log_id ASC
        `;

        const [rows] = await pool.execute(query, [lastLogId]);

        if(rows.length === 0) {
            return;
        }

        console.log(rows.length + " new CAN entry/entries detected:");
        console.table(rows);

        const newestRow = rows[rows.length - 1];
        lastLogId = Number(newestRow.log_id);
        console.log("next check will begin after log #" + lastLogId);
    } catch(error) {
        console.error("CAN log check failed:", error);
    }
}

Stage 3: broadcasting database rows as JSON

Stage 2 only printed the new rows. The next step converted each row into JSON and sent it to every connected webpage. The original plain-text connection message was also changed into a typed JSON message so the browser could distinguish it from a CAN entry. 

socket.send(JSON.stringify({
    type: "connection",
    message: "Connected to the LiF WebSocket server"
}));
// send one object to every connected webpage
function broadcast(messageObject) {
    const messageText = JSON.stringify(messageObject);
    let connectedClients = 0;

    server.clients.forEach(function(client) {
        if(client.readyState === WebSocket.OPEN) {
            client.send(messageText);
            connectedClients++;
        }
    });

    return connectedClients;
}

The following loop was added before advancing lastLogId: 

for(const row of rows) {
    const canMessage = {
        type: "can_message",
        log_id: Number(row.log_id),
        can_id: row.can_id,
        direction: row.direction,
        raw_byte: Number(row.raw_byte),
        source_controller: row.source_controller,
        logged_at: row.logged_at
    };

    const recipients = broadcast(canMessage);
    console.log("broadcast log #" + row.log_id + " to " + recipients + " webpage(s)");
}

WebSockets transmit text rather than normal JavaScript objects. JSON.stringify() converts the object into text on the server, and JSON.parse() restores it in the browser. 

{
    "type": "can_message",
    "log_id": 10,
    "can_id": "0x101",
    "direction": "rx",
    "raw_byte": 10,
    "source_controller": "EC"
}

client.html was updated to identify connection messages and CAN messages: 

socket.addEventListener("message", function(event) {
    try {
        const message = JSON.parse(event.data);
        console.log("WebSocket message received:", message);

        if(message.type === "connection") {
            messageDisplay.textContent = message.message;
            return;
        }

        if(message.type === "can_message") {
            messageDisplay.textContent = "New CAN log #" + message.log_id + ": " + message.source_controller + " sent raw byte " + message.raw_byte + " using CAN ID " + message.can_id;
        }
    } catch(error) {
        console.error("Invalid WebSocket message:", event.data);
    }
});

Stage 4: integrating the real elevator page

The proven WebSocket receiver was then added to elevator_control.js. The website connects to the same host that served the page, which works for both Windows testing and the Raspberry Pi. 

const elevatorSocket = new WebSocket("ws://" + window.location.hostname + ":8080");

const floorByEcRawByte = {
    5: "1",
    6: "2",
    7: "3"
};

let lastConfirmedFloor = "";
let liveEcPositionReceived = false;

elevatorSocket.addEventListener("message", function(event) {
    let message;

    try {
        message = JSON.parse(event.data);
    } catch(error) {
        console.error("invalid websocket message received:", event.data);
        return;
    }

    if(message.type !== "can_message") {
        return;
    }

    const isEcMessage = message.can_id === "0x101" && message.direction === "rx" && message.source_controller === "EC";

    if(!isEcMessage) {
        return;
    }

    const floor = floorByEcRawByte[Number(message.raw_byte)];

    if(!floor) {
        console.log("ignored non-position EC byte:", message.raw_byte);
        return;
    }

    liveEcPositionReceived = true;

    if(floor === lastConfirmedFloor) {
        return;
    }

    moveCarToFloor(floor, "EC");
    lastConfirmedFloor = floor;
    lastCommandDisplay.textContent = "EC confirmed Floor " + floor + " from CAN log #" + message.log_id;
});

Only messages matching all three EC fields can move the graphic:

Required field Value Reason
can_id 0x101 identifies the Elevator Controller
direction rx confirms the SC received the message
source_controller EC rejects unrelated CAN traffic

The complete position-byte mapping is:

Raw byte Binary meaning Virtual floor
5 enable bit + floor 1 Floor 1
6 enable bit + floor 2 Floor 2
7 enable bit + floor 3 Floor 3

Raw byte 10 was useful for proving Stage 3 transport, but it is not a valid position byte and is intentionally ignored by the final page.

The PHP request response was also changed so that submitting a destination does not move the graphic immediately: 

if(responseData.success === true) {
    const floor = String(responseData.requested_floor);
    lastCommandDisplay.textContent = "Request #" + responseData.elevator_request_id + " logged for Floor " + floor + " - waiting for elevator";

    // do not call moveCarToFloor here because the EC has not confirmed movement
}

This means a website request follows the physical system instead of assuming success.

Restoring the current floor after a refresh

Live WebSocket messages only reach pages connected at that moment. Refreshing destroys the page's JavaScript state, and Node does not replay old rows because it starts after the newest log_id. The page therefore originally returned to its default Floor 1 position.

I fixed this with a one-time status request when the page loads. Future changes still arrive through the WebSocket. 

function loadInitialElevatorStatus() {
    fetch("elevator_control.php?request_action=status", {
        method: "GET",
        cache: "no-store"
    })
    .then(function(response) {
        if(!response.ok) {
            throw new Error("HTTP status " + response.status);
        }

        return response.json();
    })
    .then(function(responseData) {
        if(responseData.success !== true || liveEcPositionReceived === true || responseData.position_available !== true) {
            return;
        }

        const floor = String(responseData.current_floor);

        if(!carPositions[floor]) {
            return;
        }

        moveCarToFloor(floor, "EC");
        lastConfirmedFloor = floor;
        console.log("Restored EC-confirmed Floor " + floor + " when the page loaded");
    })
    .catch(function(error) {
        console.error("Initial elevator status request failed:", error);
    });
}

// restore the latest EC-confirmed floor once when the page loads
loadInitialElevatorStatus();

The PHP status handler queries only valid EC position rows and returns JSON: 

// return the latest EC-confirmed floor when the webpage loads
if($_SERVER['REQUEST_METHOD'] === 'GET' && ($_GET['request_action'] ?? '') === 'status') {
    header('Content-Type: application/json');
    header('Cache-Control: no-store');

    $query = "
        SELECT log_id, raw_byte
        FROM can_message_log
        WHERE can_id = '0x101'
            AND direction = 'rx'
            AND source_controller = 'EC'
            AND raw_byte IN (5, 6, 7)
        ORDER BY log_id DESC
        LIMIT 1
    ";

    $statement = $pdo->query($query);
    $latestPosition = $statement->fetch();

    if(!$latestPosition) {
        echo json_encode([
            'success' => true,
            'position_available' => false,
            'current_floor' => null,
            'log_id' => null
        ]);
        exit;
    }

    $floorByRawByte = [5 => 1, 6 => 2, 7 => 3];
    $rawByte = (int) $latestPosition['raw_byte'];

    echo json_encode([
        'success' => true,
        'position_available' => true,
        'current_floor' => $floorByRawByte[$rawByte],
        'log_id' => (int) $latestPosition['log_id']
    ]);
    exit;
}

fetch() can be called without PDO::FETCH_ASSOC because the shared database connection already sets PDO::ATTR_DEFAULT_FETCH_MODE to PDO::FETCH_ASSOC.

The liveEcPositionReceived flag prevents a slower startup response from overwriting a newer floor that arrived through the WebSocket while the request was still running.

Testing, results, and issues

I tested all three floors with separate EC rows:

INSERT INTO can_message_log (can_id, direction, raw_byte, source_controller) VALUES ('0x101', 'rx', 5, 'EC');
INSERT INTO can_message_log (can_id, direction, raw_byte, source_controller) VALUES ('0x101', 'rx', 7, 'EC');
INSERT INTO can_message_log (can_id, direction, raw_byte, source_controller) VALUES ('0x101', 'rx', 6, 'EC');

The website moved Floor 1 -> Floor 3 -> Floor 2 without refreshing. Refreshing or leaving and returning to the page also restored the latest EC-confirmed floor from MariaDB.

Issue Cause Fix
Page returned to Floor 1 after refresh WebSockets do not replay messages sent before the new page connected added one startup status request to PHP
loadInitialElevatorStatus is not defined the function call was placed outside DOMContentLoaded moved the call before the final });
Unexpected token '<' while parsing JSON the PHP status branch was commented out, so the normal HTML page was returned enabled the handler, corrected success, and used exit after JSON
Regular-member JavaScript could stop early PHP does not create the admin-only maintenance button for regular members checked that the button exists before using it
Raw byte 10 did not move the elevator it was not a valid EC floor-position byte kept the explicit 5, 6, and 7 mapping

console.error() was not the cause of the JSON problem. It only displayed the exception. The < error specifically showed that response.json() received HTML beginning with <!DOCTYPE html>.

[!success] Final result The complete MariaDB -> Node -> WebSocket -> website path works. New EC position rows move the virtual elevator live, duplicate floor reports are ignored, unrelated CAN messages cannot move it, and the most recent valid position is restored after a refresh.

Current limitations and next steps

  • The Node server still polls MariaDB every 500 ms; MariaDB is not directly notifying Node
  • WebSocket messages are live and are not stored for disconnected webpages
  • The one-time PHP status query handles the missing initial state after a refresh
  • The current browser client does not automatically reconnect if Node stops
  • A later version could stream other live values, such as ToF distance, through additional JSON message types
