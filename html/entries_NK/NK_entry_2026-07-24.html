db_connect

From there, I used MR's note on what functions he wanted. The first one I made was db_connect() since that was the most logical approach - actually be able to connect/query the DB before writing functions that query it.

// attempts to establish DB connection (try-catch)
// returns true if exists or active, false if failed
bool DB::db_connect() {
    // if a connection already exists to the DB do not connect to it again
    if(con != nullptr && !con->isClosed()) { return true;}
    
    // in case con is old, delete and replace (cleanup before trying)
    if (con != nullptr) {
        delete con;
        con = nullptr;
    }

    // try to open the SQL connection
    try {
        // obtain the SQL driver
        // similar to original code
        sql::Driver* driver = get_driver_instance();

        // connect to MariaDB
        con = driver->connect("tcp://127.0.0.1:3306", "LiF_Admin", "LiF_ESE");

        // select the lif_elevator database to use
        con->setSchema("lif_elevator");

        // if everything works up until this point, no errors occured so return true
        return true;
    } catch (sql::SQLException& error) {
        // display the issue the SQL returned
        // error.what() apparently formats it to be human-readable and asks the exception for its description
        std::cerr << "Database connection failed: " << error.what() << std::endl;

        // remove any partially created or unusable connection if it failed (cleanup)
        if (con != nullptr) {
            delete con;
            con = nullptr;
        }

        // return false since the connection attempt failed
        return false;
    }
}

The function isn't overly complicated but my god does C++ syntax suck.

The comments explain it pretty well.

  1. check if the connection exists
  2. in case con exists but had issues, delete it and reset it
  3. try to form the connection
    1. make a driver pointer using the get_driver_instance() function - same one Michael uses
    2. try to connect to the localhost connection with a defined port using the LiF_Admin account
    3. set the schema being used to lif_elevator
    4. return true if all went well
  4. catch any exceptions/errors
    1. print the error and what it was
    2. if the connection exists delete and reset it
    3. return false for db connection fail

get_operation_mode

From there, I made another function that grabs the operation_state. See the related SQL note/update below in Updating elevator_state table

The function was implemented as such:

// function that grabs the current operation mode from the database
DB::OperationMode DB::get_operation_mode() {
    // make sure the DB connection exists before querying
    if(!db_connect()) { 
        return OperationMode::UNKNOWN;
    }

    // hold the SQL query statement and relevant pointers
    sql::Statement* statement = nullptr;
    sql::ResultSet* result = nullptr;

    // query the DB:
    try {
        statement = con->createStatement();

        result = statement->executeQuery(
            "SELECT operation_mode "
            "FROM elevator_state "
            "WHERE state_id = 1 "
            "LIMIT 1 "
        );

        // check if the query returned 0 rows
        // basically an empty table/queue case
        if(!result->next()) {

            // remove query objects since nothing was returned
            delete result;
            delete statement;

            // return UNKNOWN for unknown value/fail
            return OperationMode::UNKNOWN;
        }

        // grab the operation_mode
        std::string operationMode = result->getString("operation_mode");

        // obtained the mode from the line above, cleanup objects
        delete result;
        delete statement;

        // map the returned operation_mode into the enum class
        if(operationMode == "normal")
        {
            return OperationMode::NORMAL;
        } 
        else if (operationMode == "sabbath")
        {
            return OperationMode::SABBATH;
        } 
        else if (operationMode == "maintenance")
        {
            return OperationMode::MAINTENANCE;
        } 
        else if (operationMode == "fault") 
        {
            return OperationMode::FAULT;
        }

        return OperationMode::UNKNOWN;


    } catch (sql::SQLException& error) {
        // delete either object if it was created
        if (result != nullptr) {
            delete result;
        }
        if (statement != nullptr) {
            delete statement;
        }

        // print error description
        std::cerr << "Failed to read operation_mode from DB" << error.what() << std::endl;

        return OperationMode::UNKNOWN;
    }
}

Since this function is of type OperationMode (which is an enum defined as)

    enum class OperationMode {
        NORMAL,
        SABBATH,
        MAINTENANCE,
        FAULT,
        UNKNOWN
    };

The return statements must be returned as such too.

The process goes: 1) check if the DB is connected 2) create pointers for DB access 3) try to query the DB 1) select from operation_mode table and pull the elevator_state 1) if the query returned nothing delete pointers and return known state 2) if everything went w ell, grab the operation_mode using getString 3) delete pointers since they're not longer needed 4) map the read state from DB into if statements and return the appropriate OperationMode 4) If querying fails, catch it, delete pointers, and print an error message

Updating elevator_state table

After consulting MR about it and looking at the C++ code he gave me, we kind of concluded that it would be smarter to modify the existing elevator_state table. The old one was:

MariaDB [lif_elevator]> desc elevator_state;
+-----------------+---------------------+------+-----+---------------------+-------------------------------+
| Field           | Type                | Null | Key | Default             | Extra                         |
+-----------------+---------------------+------+-----+---------------------+-------------------------------+
| state_id        | tinyint(3) unsigned | NO   | PRI | NULL                |                               |
| doors_open      | tinyint(1)          | NO   |     | 0                   |                               |
| sabbath_enabled | tinyint(1)          | NO   |     | 0                   |                               |
| updated_at      | datetime            | NO   |     | current_timestamp() | on update current_timestamp() |
+-----------------+---------------------+------+-----+---------------------+-------------------------------+

Here, sabbath_enabled was it's own column, so following the Enum that MR made:

enum class OperationMode {
        NORMAL,
        SABBATH,
        MAINTENANCE,
        FAULT
    };

Storing normal operation, maintenance mode, or faulted in their own columns within the SQL would be a poor decision. This can create issues later where multiple states are triggered at once.

Because of this, it would be smarter and better to change the existing sabbath_enabled into operation_modes with pre-existing constraints of these states.

It's important to note, that the PHP and JS that handles sabbath_enabled on the website will have to be changed later!!!

Continuing with modifying the table, the following SQL command can be ran to make the change:

MariaDB [(none)]> use lif_elevator;
Database changed
MariaDB [lif_elevator]> ALTER TABLE elevator_state CHANGE COLUMN sabbath_enabled operation_mode VARCHAR(20) NOT NULL DEFAULT 'normal';
Query OK, 1 row affected (0.058 sec)               
Records: 1  Duplicates: 0  Warnings: 0

This alters the table and changes the column, but the values that existed in it prior will become literals. Since sabbath_enabled was a tinyint, the 1 that it held will not be stored as "1". This can be seen below:

MariaDB [lif_elevator]> select * from elevator_state;
+----------+------------+----------------+---------------------+
| state_id | doors_open | operation_mode | updated_at          |
+----------+------------+----------------+---------------------+
|        1 |          0 | 1              | 2026-07-24 18:12:55 |
+----------+------------+----------------+---------------------+
1 row in set (0.001 sec)

So the table will have to be updated to hold the proper default value - 'normal'

MariaDB [lif_elevator]> UPDATE elevator_state SET operation_mode = CASE WHEN operation_mode = '1' THEN 'sabbath' ELSE 'normal' END;
Query OK, 1 row affected (0.007 sec)

Additionally, let's add constraints to the table itself so it cannot suddenly become a "banana" state lol:

MariaDB [lif_elevator]> ALTER TABLE elevator_state
    -> ADD CONSTRAINT chk_operation_mode
    -> CHECK (operation_mode IN (
    -> 'normal',
    -> 'sabbath',
    -> 'maintenance',
    -> 'fault'
    -> )
    -> );
Query OK, 1 row affected (0.027 sec)               
Records: 1  Duplicates: 0  Warnings: 0
