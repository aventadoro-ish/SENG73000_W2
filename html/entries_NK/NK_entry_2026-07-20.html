Entry overview

This entry summarizes the website back-end and elevator-control work completed so far. The website can collect access requests, store them in MariaDB, authenticate approved accounts, restrict admin pages, create new users, log remote elevator requests, and store the current door and Sabbath-mode states.

Key details

  • Purpose: Create one reference entry covering the complete website-to-database workflow.
  • Components: XAMPP, MariaDB, SQL, PHP, PDO, sessions, password hashing, JavaScript, AJAX/fetch, JSON, HTML, and CSS.
  • Result: Completed the main website account cycle and the first phase of database-backed elevator controls.
  • Team contribution: Nick Kapuka

System workflow

The current website path is:

  1. The user submits a form or presses an elevator button.
  2. HTML or JavaScript sends a POST request to PHP.
  3. PHP validates the submitted values.
  4. PDO runs an SQL query against MariaDB.
  5. PHP returns either HTML or a JSON response.
  6. JavaScript updates the webpage without a full reload.

The Raspberry Pi will later read pending elevator requests and send CAN messages to the elevator controller. The website currently logs commands and simulates the visual response.

SQL and MariaDB

Four main tables were created. The first three store history and accounts, while elevator_state stores the current operating state in one permanent row.

Table Purpose
access_requests Stores pending and reviewed website-access forms
users Stores approved accounts and hashed passwords
elevator_requests Logs floor commands and their processing status
elevator_state Stores door and Sabbath-mode states

Representative SQL commands

USE lif_elevator;

SHOW TABLES;
DESCRIBE elevator_requests;
SHOW CREATE TABLE users;

SELECT *
FROM elevator_requests
ORDER BY elevator_request_id DESC;

INSERT creates a new history row, while UPDATE changes an existing row. This distinction became important for the door switch because its current state is stored by repeatedly updating state_id = 1. 

UPDATE elevator_state
SET doors_open = 1
WHERE state_id = 1;

ALTER TABLE elevator_state
ADD sabbath_enabled BOOLEAN NOT NULL DEFAULT FALSE
AFTER doors_open;

PHP, PDO, and authentication

PHP connects the forms and webpages to MariaDB. Submitted data is validated before PDO prepared statements send it to the database. 

$query = "
    SELECT *
    FROM access_requests
    WHERE request_id = :request_id
";

$statement = $pdo->prepare($query);
$statement->bindValue('request_id', $requestId, PDO::PARAM_INT);
$result = $statement->execute();
$request = $statement->fetch();

The prepared-statement order is:

  1. Store the SQL in $query.
  2. Use prepare() to create the SQL template.
  3. Bind submitted values to placeholders.
  4. Use execute() to run it.
  5. Use fetch() or fetchAll() to retrieve SELECT results.

Authentication

$passwordCorrect = $user &&
    password_verify($password, $user['password_hash']);

if ($passwordCorrect &&
    $user['account_status'] === 'approved') {
    session_regenerate_id(true);

    $_SESSION['logged_in'] = true;
    $_SESSION['user_id'] = $user['user_id'];
    $_SESSION['username'] = $user['username'];
    $_SESSION['user_role'] = $user['user_role'];
}

Admin pages check both logged_in and user_role. Session-key spelling must match exactly.

JavaScript and AJAX

AJAX allows the elevator page to contact PHP without refreshing. The project uses fetch() and JSON. 

function sendElevatorRequest(floor, sourceController) {
    const requestData = new URLSearchParams();

    requestData.append("requested_floor", floor);
    requestData.append("source_controller", sourceController);

    return fetch("elevator_control.php", {
        method: "POST",
        headers: {
            "Content-Type": "application/x-www-form-urlencoded"
        },
        body: requestData.toString()
    })
    .then(function (response) {
        return response.json();
    });
}
  • URLSearchParams creates form-style name/value data.
  • fetch() sends the background HTTP request.
  • .then() handles a fulfilled Promise.
  • .catch() handles network, decoding, or thrown JavaScript errors.
  • response.json() converts PHP's JSON into a JavaScript value.

Results and notable lessons

  • The full access cycle works: submit request, approve it as admin, create an account, and log in with the new account.
  • Floor and car-controller requests are logged with the requesting website user.
  • Door and Sabbath states are stored persistently in elevator_state.
  • Open doors prevent visual movement while still allowing the request to be logged for later processing.
  • SQL trailing commas, foreign keys, unique constraints, session-key typos, forgotten execute() calls, and string-versus-Boolean comparisons were common debugging points.

The next major phase is Raspberry Pi integration. The Pi will consume database requests, communicate over CAN, and update the database using the real elevator position and controller status. The hardware controller must enforce the real door safety interlock; the current JavaScript interlock affects only the visual webpage.
