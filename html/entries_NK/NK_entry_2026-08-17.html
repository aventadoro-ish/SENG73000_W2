Main task or topic

Since the previous interface update, I completed the functional Maintenance workflow behind the elevator control page. Maintenance is now treated as a shared database state instead of only a visual button state. PHP authorizes each action, JavaScript keeps the page synchronized, and MariaDB stores any floors that an administrator marks out of service.

The work had three main parts:

  • Prevent passenger requests and incompatible controls while Maintenance is active.
  • Store persistent per-floor lockouts in a dedicated SQL table.
  • Reformat the CAN protocol table so the routing information and Byte 0 fields are easier to read.

Maintenance as a shared operating mode

The existing elevator_state.operation_mode field remains the source of truth. The Maintenance button is generated only for administrators: 

<?php if(($_SESSION['user_role'] ?? '') === 'admin'): ?>
  <button type="button" id="maintenanceToggle">
    Maintenance Mode
  </button>
<?php endif; ?>

Hiding the button is useful for the interface, but it is not enough for security. The PHP endpoint repeats the administrator check before changing the database: 

if(($_SESSION['user_role'] ?? '') !== 'admin') {
    echo json_encode([
        'success' => false,
        'message' => 'Administrator access is required'
    ]);
    exit;
}

This prevents a regular user from bypassing the missing button by manually sending a POST request.

Preventing requests from entering the queue

The original page could still display Sending request for Floor X... while Maintenance was active. JavaScript now checks the synchronized mode before displaying that message or sending AJAX: 

function maintenanceBlocksFloorRequest() {
    if (maintenanceEnabled !== true) {
        return false;
    }

    lastCommandDisplay.textContent =
        "Floor requests are disabled while Maintenance mode is enabled";

    return true;
}

Both the floor-station buttons and cab buttons call this function before sendElevatorRequest().

The important protection is still on the server. PHP reads the current mode and returns before performing the request INSERT: 

if($elevatorState['operation_mode'] === 'maintenance') {
    echo json_encode([
        'success' => false,
        'message' => 'Floor requests are disabled while Maintenance mode is enabled',
        'operation_mode' => 'maintenance'
    ]);

    exit;
}

I also changed the final insert into a conditional INSERT ... SELECT. This protects against another user enabling Maintenance between the first state check and the database write: 

INSERT INTO elevator_requests (
    request_type,
    requested_floor,
    requested_by_user_id,
    source_controller
)
SELECT
    :request_type,
    :requested_floor,
    :requested_by_user_id,
    :source_controller
FROM elevator_state AS es
LEFT JOIN elevator_floor_lockouts AS efl
    ON efl.floor_number = :lockout_floor
WHERE es.state_id = 1
  AND es.operation_mode <> 'maintenance'
  AND COALESCE(efl.is_locked, 0) = 0;

If Maintenance or a floor lockout becomes active at the last moment, the query inserts zero rows. No passenger request is added to elevator_requests.

Sabbath and door safety interlocks

Maintenance and Sabbath share the same operation_mode column, so Sabbath must not overwrite Maintenance. PHP locks the shared row while checking the current mode: 

SELECT operation_mode
FROM elevator_state
WHERE state_id = 1
LIMIT 1
FOR UPDATE;

If the mode is already maintenance, the Sabbath request is rejected. JavaScript also disables the Sabbath button, changes its label to Unavailable during Maintenance, and applies an interlocked visual state.

Door operation received a similar restriction. During Maintenance, regular users cannot open or close the doors, while administrators retain control for authorized testing. PHP performs this check inside a transaction: 

if(
    $elevatorState['operation_mode'] === 'maintenance' &&
    !$userIsAdmin
) {
    $pdo->rollBack();

    echo json_encode([
        'success' => false,
        'message' => 'Only administrators can operate the doors while Maintenance mode is active',
        'operation_mode' => 'maintenance'
    ]);

    exit;
}

The FOR UPDATE read prevents Maintenance from changing halfway through the permission check and door-state update.

Maintenance status indicator

The Maintenance state is visible to all logged-in users even though only administrators receive the toggle. PHP outputs a status rail when the database mode is Maintenance: 

<aside class="maintenance-status-rail" id="maintenanceStatusRail"
  role="status" aria-live="polite">
  <span class="maintenance-status-light" aria-hidden="true"></span>

  <div class="maintenance-status-copy">
    <span>Restricted operation</span>
    <strong>Maintenance Mode Active</strong>
    <small>Passenger requests are paused while authorized personnel configure floor access.</small>
  </div>
</aside>

The final design uses a static amber status light, a dark notification rail, and a hazard stripe. It is noticeable without behaving like an emergency alarm. JavaScript toggles maintenance-active on the complete control page, which also changes the elevator panel perimeter.

Persistent floor-lockout table

I added elevator_floor_lockouts to store the service state of every displayed floor: 

CREATE TABLE IF NOT EXISTS elevator_floor_lockouts (
    floor_number TINYINT(3) UNSIGNED NOT NULL,
    is_locked TINYINT(1) NOT NULL DEFAULT 0,
    lockout_reason VARCHAR(255) DEFAULT NULL,
    updated_by_user_id INT(10) UNSIGNED DEFAULT NULL,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP()
        ON UPDATE CURRENT_TIMESTAMP(),

    PRIMARY KEY (floor_number),

    CONSTRAINT chk_floor_lockout_number
        CHECK (floor_number BETWEEN 1 AND 6),

    CONSTRAINT chk_floor_lockout_state
        CHECK (is_locked IN (0, 1)),

    CONSTRAINT fk_floor_lockout_user
        FOREIGN KEY (updated_by_user_id)
        REFERENCES users (user_id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

One unlocked row is inserted for each floor:

INSERT IGNORE INTO elevator_floor_lockouts (floor_number)
VALUES (1), (2), (3), (4), (5), (6);

Using INSERT IGNORE means rerunning the setup file does not overwrite saved lockout states. The primary key also guarantees that each floor has at most one current record.

Updating a floor lockout

Floor-lockout changes are accepted only when the user is an administrator and Maintenance is currently active. PHP validates the floor range and the requested locked or unlocked state before writing.

The update uses an upsert:

INSERT INTO elevator_floor_lockouts (
    floor_number,
    is_locked,
    lockout_reason,
    updated_by_user_id
)
VALUES (
    :floor_number,
    :is_locked,
    :lockout_reason,
    :updated_by_user_id
)
ON DUPLICATE KEY UPDATE
    is_locked = VALUES(is_locked),
    lockout_reason = VALUES(lockout_reason),
    updated_by_user_id = VALUES(updated_by_user_id);

This creates a missing floor record or updates the existing record without requiring separate INSERT and UPDATE branches.

Saved lockouts remain active after Maintenance is disabled. Maintenance controls when administrators may configure the lockouts; the lockout row controls whether that floor is available for service.

Synchronizing lockouts in JavaScript

PHP places the initial lockout map into the page as JSON:

data-floor-lockouts="<?php
  echo htmlspecialchars(
      json_encode($initialFloorLockouts),
      ENT_QUOTES,
      'UTF-8'
  );
?>"

JavaScript decodes it and applies each state to three related elements:

  • The building floor row.
  • The matching cab button.
  • The administrator's lockout card.
floorLockoutStates[floor] = floorIsLocked;
floorRow.classList.toggle("floor-locked", floorIsLocked);
carButton.classList.toggle("floor-locked", floorIsLocked);
lockoutCard.classList.toggle("is-locked", floorIsLocked);

The visual classes help the user understand the saved state, but PHP still checks the database before every movement request.

CAN protocol table update

The original CAN layout combined message information with eight separate bit columns. This produced a thirteen-column table that became cramped and difficult to scan.

I reduced the outer table to six columns:

  • CAN ID
  • Message
  • From
  • To
  • DLC
  • Byte 0

Byte 0 is now an eight-column CSS Grid inside the final cell. For example, the SC command byte is written as: 

<div class="CANprotocol-byte-map">
  <span class="CANprotocol-bit-cell CANprotocol-unused" data-bit="7">—</span>
  <span class="CANprotocol-bit-cell CANprotocol-unused" data-bit="6">—</span>
  <span class="CANprotocol-bit-cell CANprotocol-unused" data-bit="5">—</span>
  <span class="CANprotocol-bit-cell CANprotocol-unused" data-bit="4">—</span>
  <span class="CANprotocol-bit-cell CANprotocol-unused" data-bit="3">—</span>
  <span class="CANprotocol-bit-cell CANprotocol-enable" data-bit="2">SC_EN</span>
  <span class="CANprotocol-bit-cell CANprotocol-request CANprotocol-span-2"
    data-bit="1–0">SC_FloorReq</span>
</div>

The grid rule is:

.CANprotocol-byte-map {
  display: grid;
  grid-template-columns: repeat(8, minmax(0, 1fr));
  gap: 5px;
  min-width: 520px;
}

.CANprotocol-span-2 {
  grid-column: span 2;
}

Each cell displays its bit number, unused bits use a muted dash, and multi-bit fields span the correct number of columns. The existing enable/status, position, and floor-request colours remain connected to the legend. The outer wrapper still provides horizontal scrolling on narrow screens.

I also corrected the Floor 2 and Floor 3 row descriptions and replaced the invalid rowspawn attributes in the field-definition table with proper scoped headers.

Result

Maintenance is now enforced through the entire request path instead of only through page text. Regular users cannot queue floor requests, operate the doors, or enable Sabbath while Maintenance is active. Administrators can configure persistent per-floor lockouts, and every request is validated against both the current operation mode and the selected floor's database record.

The CAN documentation now presents the same byte definitions in a much more readable format. Message routing can be scanned from left to right, while the nested bit strip still shows the exact Byte 0 allocation from bit 7 to bit 0.

Proof of Functionality

  • Maintenance mode shows the restricted-operation status rail to every user.
  • Regular users receive disabled door and Sabbath controls during Maintenance.
  • Floor and cab requests are rejected without adding rows to elevator_requests.
  • Administrator floor lockouts remain saved after the page is refreshed or Maintenance is disabled.
  • The CAN protocol page displays all seven message definitions with complete eight-bit maps.
