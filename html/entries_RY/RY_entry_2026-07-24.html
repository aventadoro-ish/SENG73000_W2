Logbook Entry

Summary

Verified which SQL schema actually matches the live setup, traced a "diagnostics page isn't connected" report to a bad assumption in db.php, and added a second table to elevator_diagnostics.php after feedback from Nick that the page behaved more like a CAN translation table than a full diagnostic report. Also designed can_message_log, a new table for recording actual CAN bus traffic, and found a compile-breaking bug in the RPi4 CAN receive code.

Schema Verification

Compared two SQL dumps against the live setup. elevator_schema.sql turned out to be a stale dump: different database name, and missing elevator_requests and elevator_state entirely. lif_elevator.sql matched the actual MySQL 8.4 / Ubuntu LAMP stack and was confirmed as the live schema.

Tracing the Connection Bug

Traced a "diagnostics page isn't connected" report from teammates to db.php using $host = 'localhost', which is only correct if MySQL and Apache/PHP share a machine. Confirmed that MySQL actually lives on the RPi4, not the VM running Apache.

Documented the RPi4-side changes needed for a remote connection: setting bind-address, granting LiF_Admin access from the VM's IP, and opening the firewall port, plus a mysql -h command to test the connection before trusting the PHP page.

Computed CAN Byte Decoding

Since elevator_requests has no stored raw payload byte, added encodeCanByte() to reconstruct Byte 0 (hex and bit breakdown) from source_controller and requested_floor, based on the EN-bit/floor-bits layout from the CAN Protocol Reference table. Flagged this as inferred from documentation, not verified against firmware.

Feedback from Nick

Nick reviewed the diagnostics page and felt it was solid as a human-readable CAN translation table, but noted it wasn't yet a full diagnostic page. His suggestion was to keep the existing table as-is and add a second table answering: what type of request was it, which account requested the elevator, from what source, whether it was approved, whether it was denied, and whether it failed or succeeded.

He mapped each question to a column already sitting in elevator_requests: request_type, requested_by_user_id, source_controller, accepted_at, completed_at, and failure_reason, and suggested either a full explicit column list or simply querying the whole table.

Request Details Table

Went with the simpler of the two options and added a second query, SELECT * FROM elevator_requests, in its own try/catch block: 

$requestDetails = [];
$detailsLoadError = '';

try {
    $detailsQuery = "SELECT * FROM elevator_requests ORDER BY requested_at DESC";
    $detailsStatement = $pdo->prepare($detailsQuery);
    $detailsStatement->execute();
    $requestDetails = $detailsStatement->fetchAll(PDO::FETCH_ASSOC);
} catch (PDOException $e) {
    error_log($e->getMessage());
    $detailsLoadError = "Could not load request details right now. Please try again shortly.";
}

Paired it with a Request Details table showing request_type, requested_by_user_id, source_controller, accepted_at, completed_at, and failure_reason, answering Nick's what/who/from-where/approved/completed/failed questions per request.

Later added derived Approved, Succeeded, and Failed Yes/No columns based on IS NOT NULL checks on the three timestamp/reason columns, using a small helper: 

function yesNo(bool $isTrue): string {
    return $isTrue ? "Yes" : "No";
}

diagnostics.js Refactor

Refactored diagnostics.js into a reusable initDiagnosticsTable() function so multiple tables on the same page get independent search, sort, and pagination instead of sharing state. Also added the "Back to Members" / "Log Out" button row, and fixed the CAN Protocol Reference link to point at ../html/CAN_protocol.html.

Designing can_message_log

Designed can_message_log, a new table to hold actual CAN bus traffic: direction, raw byte, CAN ID, DLC, source controller, and timestamp, with a nullable foreign key back to elevator_requests for non-broadcast messages. Wrote can_message_log.sql to create it. 

CREATE TABLE can_message_log (
    log_id int(10) unsigned NOT NULL AUTO_INCREMENT,
    elevator_request_id int(10) unsigned DEFAULT NULL,
    can_id varchar(6) NOT NULL,
    direction enum('tx','rx') NOT NULL,
    raw_byte tinyint(3) unsigned NOT NULL,
    dlc tinyint(3) unsigned NOT NULL DEFAULT 1,
    source_controller varchar(30) NOT NULL,
    logged_at datetime NOT NULL DEFAULT current_timestamp(),
    PRIMARY KEY (log_id),
    CONSTRAINT fk_can_log_request FOREIGN KEY (elevator_request_id)
        REFERENCES elevator_requests (elevator_request_id)
        ON DELETE SET NULL ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;

Engineering Discussion

Nick's feedback was a useful reframe: the page was a correct CAN translation table, but a diagnostic page also needs to answer who/what/why for each request, not just what the bytes on the wire look like. Reusing the whole row via SELECT * for the details table was the more pragmatic choice given the schema is small and stable, versus maintaining a second explicit column list in parallel with the first query.

Designing can_message_log now, ahead of anything actually writing to it, sets up the next step cleanly: once pcan_functions.cpp logs to the table instead of only printing, the diagnostics page will have a third, real-traffic table to read from.
