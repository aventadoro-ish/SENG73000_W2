Summary

Objective

Investigated possible methods of implementing floor announcement audio for the Lithium Firefly elevator project. The objective was to determine how I²S could be incorporated into the existing Raspberry Pi 4 Supervisory Controller (SC), CAN network, and ESP32-S3 Car Controller (CC) while maintaining the modular architecture already developed for the project.

Research and Design Investigation

Several implementation options were evaluated for generating audio announcements whenever the elevator finite state machine enters the STATE_ARRIVED state.

Option 1 — ESP32-S3 Using Its Native I²S Peripheral

  • Use the ESP32-S3 as the dedicated audio controller.
  • The Raspberry Pi transmits a CAN message after arriving at a floor.
  • The ESP32-S3 receives the CAN message.
  • The floor number is decoded.
  • The corresponding audio file is selected.
  • The ESP32 outputs digital audio through its integrated I²S peripheral.
  • An external amplifier drives the speaker.

Advantages

  • Uses the existing CAN architecture.
  • Keeps the Supervisory Controller focused on elevator control.
  • Maintains the distributed embedded design.
  • Demonstrates integration of CAN communication and I²S.

Option 2 — Raspberry Pi Audio Output

  • Connect a powered speaker directly to the Raspberry Pi.
  • Execute the following command when entering STATE_ARRIVED.

aplay floor2.wav

Advantages

  • Simple implementation.
  • Requires very little software development.
  • No additional embedded hardware.

Disadvantages

  • Does not demonstrate I²S communication.
  • Depends on the Linux audio subsystem.
  • Less representative of an embedded implementation.

Option 3 — Raspberry Pi with MAX98357 I²S DAC

  • Use the Raspberry Pi's native I²S peripheral.
  • Connect GPIO I²S pins to a MAX98357 DAC/amplifier.
  • Execute aplay after entering STATE_ARRIVED.
  • The DAC converts the digital I²S stream into amplified speaker output.

Advantages

  • Uses true I²S communication.
  • Excellent digital audio quality.
  • Relatively little software complexity.

Architecture Considerations

The current elevator architecture already follows a distributed embedded design where the Raspberry Pi executes the elevator finite state machine while communicating with subsystem controllers over CAN. 


RPi4 (Supervisory Controller)
            |
            | CAN
            |
     ESP32-S3 (Car Controller)
            |
           I²S
            |
    Audio Amplifier
            |
         Speaker

This architecture allows the Supervisory Controller to remain responsible for elevator operation while the Car Controller manages passenger-facing features such as floor announcements.

Recommended Design

After comparing the available approaches, the preferred solution is to use the ESP32-S3 as the dedicated audio controller.

Proposed Sequence of Operation

  • The FSM transitions into STATE_ARRIVED.
  • The Raspberry Pi sends the destination floor over CAN.
  • The ESP32-S3 receives the CAN message.
  • The correct audio file is selected.
  • The ESP32 transmits digital audio through I²S.
  • The amplifier drives the speaker.

This solution preserves the modular architecture of the elevator while demonstrating integration between CAN communication, finite state machine control, and digital I²S audio.

Next Steps

  • Determine GPIO and I²S pin assignments.
  • Create a CAN message format for audio announcements.
  • Prototype audio playback on the ESP32-S3.
  • Integrate the audio system into the FSM STATE_ARRIVED transition.
