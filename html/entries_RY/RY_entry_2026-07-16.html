Project: Lithium Firefly Elevator
Hours: 7
Focus: I²S Audio Integration and Platform Investigation

Summary

Researched and attempted implementation of I²S audio floor announcements using a MAX98357A amplifier connected to a Raspberry Pi 5. Although the hardware wiring and software configuration were completed, investigation identified a compatibility issue with Raspberry Pi OS Trixie. A decision was made to continue implementation on the project Raspberry Pi 4 running Bookworm.

Objective

Investigate how digital floor announcements can be integrated into the Lithium Firefly elevator using I²S audio. The objective was to configure a MAX98357A I²S amplifier module and evaluate whether the Supervisory Controller could play floor announcements whenever the finite state machine enters STATE_ARRIVED.

Hardware Setup

A Raspberry Pi 5 was used as a temporary development platform while waiting for access to the team's Raspberry Pi 4 Supervisory Controller. The MAX98357A digital I²S amplifier was wired according to the following connections.

MAX98357A Connections

  • BCLK → GPIO18 (Pin 12)
  • LRC → GPIO19 (Pin 35)
  • DIN → GPIO21 (Pin 40)
  • GND → Pin 6
  • VIN → Pin 2 (5 V)

Software Configuration

Several software configurations were investigated while attempting to enable the MAX98357A under Raspberry Pi OS.

Configuration Attempts

  • Initially configured dtoverlay=hifiberry-dac, which was determined to be the incorrect device overlay.
  • Updated the configuration to use dtparam=i2s=on together with dtoverlay=max98357a,no-sdmode.
  • Attempted configuration using raspi-config, but encountered conflicts between PipeWire and PulseAudio.
  • Attempted both the legacy Lua configuration and the new WirePlumber 0.5 configuration format.
  • Verified available audio devices using pw-cli list-objects.

Troubleshooting

Although the hardware wiring was verified, the MAX98357A audio device never appeared within PipeWire. Only the Raspberry Pi's HDMI audio device was detected. 


pw-cli list-objects

This indicated that the operating system was not successfully loading the MAX98357A device tree overlay.

Root Cause Investigation

Further research identified that Raspberry Pi OS Trixie (Debian 13.5, Kernel 6.18.33) currently contains a known regression affecting MAX98357A I²S audio initialization. Community reports indicate that PipeWire and WirePlumber 0.5 do not correctly initialize the overlay, preventing the audio device from appearing within ALSA or PipeWire.

Since this issue is platform-specific rather than application-specific, continuing development on the Raspberry Pi 5 would provide little benefit until the operating system bug is resolved.

Engineering Decision

Rather than spending additional time troubleshooting an operating system regression, I chose to visit the lab the next day and try operating with the RPi4. The project Raspberry Pi is running Raspberry Pi OS Bookworm, where the MAX98357A overlay has been verified to operate correctly.

Implementation Plan for Raspberry Pi 4

Prepared a complete deployment procedure so the audio subsystem can be configured immediately once access to the project Raspberry Pi is available.

Planned Tasks

  • Verify Raspberry Pi OS Bookworm installation.
  • Enable I²S within config.txt.
  • Load the MAX98357A device tree overlay.
  • Verify audio device detection using aplay -l.
  • Install ALSA utilities and speech synthesis packages.
  • Generate WAV floor announcements using espeak.
  • Verify playback through the MAX98357A amplifier.
  • Integrate audio playback into the FSM STATE_ARRIVED state.
  • Record floor announcements within the project MySQL database.

Future Software Integration

Once the hardware is operating correctly on the Raspberry Pi 4, the Supervisor Controller FSM will automatically play the appropriate floor announcement whenever the elevator reaches its destination. 


void announceFloor(int floor)
{
    std::string cmd =
        "aplay /home/pi/audio/floor" +
        std::to_string(floor) +
        ".wav &";

    system(cmd.c_str());
}

The function will be called immediately after entering STATE_ARRIVED, ensuring that the announcement is played without blocking the elevator finite state machine.

Lessons Learned

This investigation demonstrated the importance of separating hardware issues from software implementation problems. Although the I²S hardware and application design were valid, platform-specific operating system changes prevented successful deployment. Identifying the root cause early prevented unnecessary debugging and allowed a practical decision to continue development on supported hardware.
