Logbook Entry

Summary

Added a third query/section to elevator_diagnostics.php so the diagnostics page actually reads from can_message_log, rather than only from elevator_requests. Matvey flagged that there was no CAN table backing the page, and he and Nick continued working through the remaining issues on the diagnostics page after this was wired in.

← Return to Logbook Cover Page

Matvey's Comment

Matvey pointed out that the diagnostics page had nowhere to actually pull CAN bus traffic from — can_message_log existed as a table from the 24th, but nothing on the page queried it yet. With the table now in place, the next piece was reading from it the same way the other two sections already read from elevator_requests.

Querying can_message_log

Added a third try/catch block to elevator_diagnostics.php, following the same pattern as the existing two queries: 

$canLog = [];
                $canLogError = '';

                try {
                    $canLogQuery = "SELECT * FROM can_message_log ORDER BY logged_at DESC";
                    $canLogStatement = $pdo->prepare($canLogQuery);
                    $canLogStatement->execute();
                    $canLog = $canLogStatement->fetchAll(PDO::FETCH_ASSOC);
                } catch (PDOException $e) {
                    error_log($e->getMessage());
                    $canLogError = "Could not load the CAN message log right now. Please try again shortly.";
                }

Third Table on the Page

Paired the query with a matching third table showing Log ID, Request ID, CAN ID, Direction, Raw Byte in hex, DLC, Source Controller, and Logged At. Registered it with the same initDiagnosticsTable() search and pagination helper already used by the CAN translation table and the Request Details table, so all three sections behave consistently.

Remaining Issues

Wiring in the query didn't clear up everything on the page. Nick and Matvey continued working through the remaining issues on the diagnostics page after this change went in, since there were still problems to sort out beyond just missing the CAN log query.

Current Status

The table and query are live, but can_message_log is still empty — nothing on the RPi4 inserts into it yet. The page will correctly show "no matching rows" until real CAN traffic starts getting logged.

Engineering Discussion

Reusing the same try/catch and initDiagnosticsTable() pattern for the third section kept the new code consistent with the rest of the page instead of introducing a one-off way of loading and rendering the CAN log data. The table being wired in but empty is expected at this stage: the database side is ready, but the RPi4 firmware side still only prints to the console instead of writing to MySQL.
